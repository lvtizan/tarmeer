# Tarmeer 商品 / 企业信息同步对接文档

> 面向合作方开发，描述如何把贵方的商品目录与企业信息自动同步到 Tarmeer 平台。
> 版本：v1（2026-06-24）

---

## 1. 概述

- **方向**：贵方在商品/企业信息发生变更时，**主动调用**本文档的 HTTP 接口把数据推送给我们（Push 模式）。
- **触发时机**：商品「创建 / 编辑 / 上架 / 下架」、企业信息「修改」时各推一次。
- **匹配方式**：每个商品用贵方自己的 **SPU id** 作为稳定唯一标识（`external_id`），我们据此判断新增还是更新，同一商品重复推送不会产生重复记录。
- **数据可见性**：推送成功后数据先进入我方审核池，**审核通过后**在站点对外可见（首次接入需审核，详见 §9）。

---

## 2. 基本约定

| 项 | 值 |
|---|---|
| 生产 Base URL | `https://www.tarmeer.com/api/partner-sync`（联调用 staging 地址我方另行提供） |
| 协议 | HTTPS |
| 方法 | POST（查询类为 GET） |
| Content-Type | `application/json; charset=utf-8` |
| 编码 | UTF-8 |
| 凭证 | `partner_key` + `secret`，由我方分配后线下提供 |

---

## 3. 鉴权与签名（重点）

每个请求必须带以下 3 个请求头：

| 请求头 | 说明 |
|---|---|
| `X-Partner-Key` | 我方分配的 partner_key（公开标识） |
| `X-Timestamp` | 请求时的 Unix 时间戳（**秒**，字符串）。我方校验与服务器时间相差不超过 **5 分钟**，超出拒绝（防重放） |
| `X-Signature` | 对请求体的 HMAC-SHA256 签名（hex 小写），算法见下 |

### 签名算法

```
待签名字符串 = X-Timestamp 的值 + "\n" + 请求体原文(rawBody)
X-Signature   = HMAC-SHA256(secret, 待签名字符串) 的十六进制小写字符串
```

> ⚠️ **最常见的联调坑**：签名用的 `rawBody` 必须与实际发送的 HTTP body **逐字节完全一致**（同样的序列化结果、空格、Unicode 转义）。请先把对象序列化成字符串，**用这个字符串既算签名、又作为 body 发送**，不要分别序列化两次。

### 示例代码

**Node.js**
```js
const crypto = require('crypto');

function sign(payload, partnerKey, secret) {
  const timestamp = Math.floor(Date.now() / 1000).toString();
  const rawBody = JSON.stringify(payload);          // 这个字符串既用于签名也用于发送
  const signature = crypto
    .createHmac('sha256', secret)
    .update(`${timestamp}\n${rawBody}`)
    .digest('hex');
  return {
    headers: {
      'Content-Type': 'application/json; charset=utf-8',
      'X-Partner-Key': partnerKey,
      'X-Timestamp': timestamp,
      'X-Signature': signature,
    },
    body: rawBody,
  };
}
```

**PHP**
```php
function sign($payload, $partnerKey, $secret) {
  $timestamp = (string) time();
  // 固定序列化方式，保证两端一致
  $rawBody = json_encode($payload, JSON_UNESCAPED_UNICODE | JSON_UNESCAPED_SLASHES);
  $signature = hash_hmac('sha256', $timestamp . "\n" . $rawBody, $secret);
  return [
    'headers' => [
      'Content-Type: application/json; charset=utf-8',
      'X-Partner-Key: ' . $partnerKey,
      'X-Timestamp: ' . $timestamp,
      'X-Signature: ' . $signature,
    ],
    'body' => $rawBody,   // 必须发送这个字符串本身
  ];
}
```

**Python**
```python
import time, hmac, hashlib, json

def sign(payload, partner_key, secret):
    timestamp = str(int(time.time()))
    raw_body = json.dumps(payload, ensure_ascii=False, separators=(',', ':'))
    signature = hmac.new(
        secret.encode(), f"{timestamp}\n{raw_body}".encode(), hashlib.sha256
    ).hexdigest()
    headers = {
        'Content-Type': 'application/json; charset=utf-8',
        'X-Partner-Key': partner_key,
        'X-Timestamp': timestamp,
        'X-Signature': signature,
    }
    return headers, raw_body  # 用 raw_body 作为请求 body 发送
```

## 4. 公共请求字段

所有 POST 请求体顶层都应包含（放在与业务数据平级的最外层）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `version` | string | 是 | 接口版本，当前固定 `"1"` |
| `request_id` | string | 是 | 本次请求的唯一 ID（UUID）。网络重试时**沿用同一个 request_id**，我方据此去重，不会重复入库 |
| `default_lang` | string | 是 | 本批内容的兜底语言（如 `en`）。多语言字段缺某语言时，我方回退到它 |

## 5. 接口列表

### 5.1 创建商品 — `POST /products/create`

贵方「商品创建」事件时调用。请求体：

> **多语言说明（重点）**：我方平台是多国多语言站点。文本字段（`title`/`description`/`category_path`）请用 **「语言码 → 文本」对象**提供译文。需提供的语言由我方分配给贵方的国家决定：英语 `en`、越南语 `vi`、阿语 `ar`。某字段缺某语言时，我方回退到 `default_lang`。电话、网址、图片 URL 等语言中立字段保持普通字符串。

```jsonc
{
  "version": "1",
  "request_id": "uuid",
  "default_lang": "en",                    // 本批兜底语言
  "items": [
    {
      "external_id": "SPU-10086",          // 必填，贵方 SPU id，稳定唯一
      "status": "active",                  // active=上架 / inactive=下架
      "title":       { "en": "High-strength nylon rope", "vi": "Dây nylon cường lực cao" },
      "description": { "en": "...", "vi": "..." },
      "category_id": "C-30021",            // 贵方叶子分类的稳定ID（可选，防改名）
      "category_path": {                   // 3 级分类全路径（顶级→二级→叶子），按语言分组
        "en": ["Consumer Electronics", "Computers & Office", "Projectors"],
        "vi": ["Điện tử tiêu dùng", "Máy tính & Văn phòng", "Máy chiếu"]
      },
      "images": ["https://你们域名/img/a.jpg", "https://你们域名/img/b.jpg"],
      "sort_order": 0,
      "attributes": {
        "skus": [
          { "sku_id": "SKU-1", "spec": "红色/10米" },
          { "sku_id": "SKU-2", "spec": "蓝色/20米" }
        ]
        // 其余贵方私有字段可任意放在 attributes 里，我方原样保存
      }
    }
  ]
}
```

- 单次 `items` 最多 **100** 条。
- 若 `create` 收到的 `external_id` 已存在，我方自动当作更新处理（不会报错），响应里 `action` 会标为 `updated`。

### 5.2 更新商品 — `POST /products/update`

贵方「商品编辑 / 上架 / 下架」事件时调用。**请求体格式与创建接口完全相同。**

- 编辑：推送商品最新字段。
- 上架/下架：把该商品的 `status` 设为 `active` / `inactive` 推过来即可，我方实时显隐，商品记录与 id 保留。
- 若 `update` 收到尚未创建过的 `external_id`，我方自动当作创建处理（不丢数据），响应里 `action` 标为 `created`。

### 5.3 企业信息 — `POST /company`

贵方供应商修改企业信息后调用（一个合作方对应一条企业记录，重复推送即更新）：

```jsonc
{
  "version": "1",
  "request_id": "uuid",
  "default_lang": "en",
  "company": {
    "company_name":  { "en": "ABC Industrial Co., Ltd.", "vi": "..." },
    "description":   { "en": "...", "vi": "..." },
    "store_address": { "en": "...", "vi": "..." },
    "categories":    { "en": ["Industrial Ropes", "Packaging"], "vi": ["...", "..."] },
    "contact_phone": "+86 138...",
    "website": "https://...",
    "whatsapp": "+86 138...",
    "logo_url": "https://你们域名/logo.png",
    "cover_image_url": "https://你们域名/cover.jpg",
    "attributes": { "任意私有字段": "原样保存" }
  }
}
```

### 5.4（可选）硬删除对账 — `POST /products/reconcile`

**仅用于商品被彻底删除（id 不再存在）的兜底场景**；日常上下架请用 §5.2 的 `status` 字段，不要依赖此接口。

```jsonc
{ "version": "1", "request_id": "uuid", "external_ids": ["SPU-1", "SPU-2", "..."] }
```

处理：贵方发来「当前全部商品 SPU id 清单」，我方把不在清单里的商品标记为已删除并下线。贵方评估能否提供该清单；做不了也可不实现，那类商品将保持最后已知状态。

### 5.5 查询同步状态 — `GET /products/status?external_id=SPU-10086`

返回该商品在我方的审核态与上下架态，便于贵方排查：

```jsonc
{ "external_id": "SPU-10086", "review_status": "approved", "listing_status": "active", "visible": true }
```

## 6. 字段说明

> 标注「i18n」的字段为多语言对象（`{ "en": "...", "vi": "..." }`），其余为普通值。`default_lang` 在请求体顶层，必填。

### 商品字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `external_id` | string | 是 | 贵方 SPU id，稳定唯一，匹配键 |
| `status` | string | 是 | `active`=上架，`inactive`=下架 |
| `title` | i18n | 是 | 商品标题，按语言提供 |
| `description` | i18n | 否 | 商品描述 |
| `category_id` | string | 否 | 贵方叶子分类的稳定 ID（防改名，便于我方映射） |
| `category_path` | i18n（值为数组） | 否 | 3 级分类全路径 `[顶级, 二级, 叶子]`，每种语言一份 |
| `images` | string[] | 否 | 图片 URL 数组，第一张为主图。我方会下载到自有 CDN，**请把我方服务器域名加入贵方图片防盗链白名单** |
| `sort_order` | number | 否 | 排序，越小越靠前，默认 0 |
| `attributes` | object | 否 | 标准字段以外的任意信息（含 SKU 列表），原样保存 |

### 企业字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `company_name` | i18n | 是 | 企业名称 |
| `description` | i18n | 否 | 企业简介 |
| `store_address` | i18n | 否 | 地址 |
| `categories` | i18n（值为数组） | 否 | 经营类目 |
| `contact_phone` | string | 否 | 联系电话（语言中立） |
| `website` | string | 否 | 官网 |
| `whatsapp` | string | 否 | WhatsApp |
| `logo_url` / `cover_image_url` | string | 否 | 图片 URL，同样需加白名单 |
| `attributes` | object | 否 | 其余私有字段 |

## 7. 响应格式与错误码

### 商品接口响应（逐条结果，部分失败不影响其余条目）

```jsonc
{
  "results": [
    { "external_id": "SPU-10086", "ok": true,  "action": "created", "review_status": "pending" },
    { "external_id": "SPU-10087", "ok": true,  "action": "updated", "review_status": "pending" },
    { "external_id": "SPU-10088", "ok": false, "error": "title required" }
  ]
}
```

| HTTP 状态 | 含义 | 处理建议 |
|---|---|---|
| 200 | 已受理（逐条看 `results`） | 检查每条 `ok` |
| 400 | 请求体格式错误 / 缺公共字段 | 修正后重发 |
| 401 | 签名校验失败 / 时间戳超期 | 检查 secret、时间同步、rawBody 一致性 |
| 429 | 触发限流 | 退避后重试（沿用同一 request_id） |
| 5xx | 我方服务异常 | 退避重试（建议指数退避，沿用同一 request_id） |

---

## 8. 重试与幂等

- 网络失败/超时请重试，**沿用同一个 `request_id`**，我方据此去重，不会重复入库。
- 商品按 `external_id` 幂等：重复推送结果一致，库里只有一条。
- 建议指数退避重试（如 1s / 2s / 4s / 8s / 16s）。

---

## 9. 数据上线说明

- 首次接入：贵方推送的企业/商品数据先进入我方审核池，审核通过后在站点对外可见。
- 后续更新是否需重新审核由我方配置，不影响贵方推送方式。
- 商品对外可见 = 我方审核通过 **且** `status=active` **且** 未被删除。

## 10. 联调 Checklist

1. 我方提供 `partner_key`、`secret`、staging Base URL。
2. 贵方用 §3 示例实现签名，先调 `GET /products/status` 或发一条测试商品验证签名通过（不再返回 401）。
3. 验证创建 → 更新（同 external_id）→ 下架（status=inactive）→ 重新上架 全流程。
4. 确认图片 URL 我方可正常下载（域名白名单已设置）。
5. 我方审核测试数据并确认站点展示正确，再切生产。
